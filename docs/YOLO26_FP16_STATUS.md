## Decision

```text
YOLO26 full-I/O FP16 accepted: yes, but keep-I/O FP16 remains the best local path.
```

This is an isolated R&D result. It does not change the frozen YOLO11
production policy.

## Candidate Matrix

| Candidate | Input dtype | Output dtype | CPU oracle | rt204 EP | App status | Decision |
| --- | --- | --- | --- | --- | --- | --- |
| FP32 e2e baseline | float32 | float32 | pass | pass | pass | baseline |
| Native FP16 direct keep-IO | float32 | mixed | load fail at `/model.23/Cast_2` | not run | no | rejected |
| Native FP16 direct full-IO | float16 | mixed | load fail at `/model.23/Cast_2` | not run | no | rejected |
| Native body-FP16/head-FP32 keep-IO | float32 | float16 | pass | pass | pass | accepted R&D FP16 baseline and best local path |
| Native body-FP16/head-FP32 full-IO | float16 | float16 | pass | pass | pass after dtype contract fallback | accepted, but not faster than keep-IO |
| XSlim FP16 | float32 | mixed | load fail at `/model.23/Concat_6` | load fail | no | rejected |

The accepted model keeps the app input in float32, converts the non-head body to
FP16, and leaves the YOLO26 head in FP32-sensitive form. This avoids the invalid
mixed-type head generated by direct full-model conversion and by XSlim FP16.

## Full-I/O FP16 Gate

The full-I/O body-FP16/head-FP32 candidate uses float16 input and float16
output. The app originally rejected it because rt204 session metadata fallback
classified the input as float32. A narrow YOLO26 R&D dtype-contract fallback was
added so the app can explicitly route this known full-I/O artifact as FP16 I/O.

| Metric class | keep-IO FP16 mean ms | keep-IO FPS | full-I/O FP16 mean ms | full-I/O FPS | Decision |
| --- | ---: | ---: | ---: | ---: | --- |
| `perf_test forward` | 379.777774 | 2.633119 | 380.472087 | 2.628314 | keep-IO slightly faster |
| `app forward-only` | 383.229967 | 2.609399 | 388.609808 | 2.573275 | keep-IO faster |
| `app full image benchmark` | 398.091562 | 2.511985 | 399.345008 | 2.504100 | effectively tied, keep-IO faster |

Full-I/O FP16 is accepted for correctness and rt204 execution. It is not the
best local path because it does not beat keep-IO FP16 and it requires FP16 app
input handling.

## Caveats

- This is an R&D baseline, not a production FPS claim.
- The accepted best FP16 artifact is not a pure full-graph FP16 model; the head
  is intentionally left FP32-sensitive to preserve ONNX Runtime loadability and
  semantic parity.
- Full-I/O FP16 is app-compatible after the explicit YOLO26 dtype-contract
  fallback, but it is not faster than keep-IO FP16.
- XSlim FP16 is not usable for the current YOLO26 e2e graph.

## Next Step

Use the body-FP16/head-FP32 keep-IO model as the YOLO26 FP16 R&D baseline.
Treat full-I/O FP16 as accepted but secondary. Treat XSlim FP16 as rejected
until the head mixed-dtype issue is fixed upstream or by a separate graph pass.
